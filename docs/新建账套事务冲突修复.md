# 新建账套预置科目事务冲突修复

## 目标与现象

新建账套报「写入预置科目表：cannot start a transaction within a transaction」。修复预置科目的事务归属，确保建账成功且失败时所有建账数据一起回滚。

## 代码调查与原因

- 桌面 CreateBook → service.CreateBook → sqlite.CreateBook。
- sqlite.CreateBook 使用 WithTx 开启事务，依次写账套、纳税人身份历史、预置科目和会计期间。
- 内嵌 seed_accounts.sql 本身还包含 BEGIN TRANSACTION / COMMIT，直接放进上述事务执行必然触发嵌套事务错误。
- 当前源码已有 stripTxControl，包含 CRLF 处理，因此不能仅凭报错断言用户正在运行当前源码对应的程序。当前程序版本与现场具体触发条件尚未确认。
- 不再让预置数据携带第二套事务控制，从源头消除对运行时删行的依赖。保留现有过滤器作为兼容防护，不扩展为通用 SQL 解析器。

## 技术方案与涉及模块

1. 删除 seed_accounts.sql 中的 BEGIN TRANSACTION 和 COMMIT，保持全部 191 条科目数据原样。更新文件头和相关注释，明确事务由调用方提供。
2. 在 strip_tx_test.go 中直接使用真实 SQLite 事务执行未经过滤的内嵌脚本，覆盖 LF、CRLF。验证写入 191 科目，并通过主动返回错误验证外层事务可完整回滚；原实现应因嵌套 BEGIN 失败。
3. 在 book_test.go 中增加真实建账后半段失败回归：期间写入触发错误时，已写入的账套、纳税人历史和科目均回滚；解除故障后同库可重试成功。

## 接口与数据流

无公开接口、数据库结构、科目编码或金额规则变更。正常流程仍为 UI → service → WithTx（账套与身份 → 科目 → 期间）→ commit；异常统一 rollback。

## 边界与影响

- LF/CRLF 检出均可运行，不能靠换行符决定事务是否正确。
- 种子文件单独手工运行时，由调用方显式开启事务；不得重新给内嵌脚本增加 BEGIN/COMMIT。
- 不修改既有用户账套，不自动清理现场失败文件。
- 源码修复须重新构建程序才能作用于已安装桌面端；当前现场旧程序是否已包含 CRLF 修复仍未知。
